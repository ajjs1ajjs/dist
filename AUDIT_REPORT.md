# Технічний аудит `dist`

**Дата:** 24 жовтня 2026 року (Europe/Kiev). **Обсяг:** лише робоча копія `E:\Code\dist`. **Статус:** аналіз коду й конфігурації без змін застосунку та без доступу до production. На початку аудиту в робочій копії вже були незакомічені зміни в HTML/CSS/SVG; висновки щодо цих файлів стосуються саме поточної робочої копії.

## 1. Executive Summary

`dist` — публічний канал розповсюдження інсталяторів і релізів та статичний GitHub Pages хаб. У ньому також є дві готові PWA-збірки, збирач ігорних знижок, Cloudflare Worker для запуску розкладу та GitHub Actions для публікації даних і синхронізації версій. Вихідний код більшості продуктів і PWA перебуває поза цим репозиторієм; їхній внутрішній аудит тут неможливий.

**Оцінка: 66/100; ризик: високий; упевненість: середня.** Це оцінка саме каналу дистрибуції та наявної тут логіки, не сертифікація продуктів. **Знахідки: P0 — 0, P1 — 3, P2 — 4, P3 — 2.** Найсуттєвіше: (1) порожня успішна відповідь Steam може стерти опублікований каталог; (2) інсталятор BCK за замовчуванням приймає архів без checksum; (3) відсутні Telegram credentials означають «успішне» надсилання і запис у історію; (4) повідомлення надсилаються до надійної публікації стану; (5) критичні сценарії не мають автоматизованих тестів.

### Статус виправлень після аудиту

У наступній роботі після аудиту виправлено захист Steam snapshot і timestamp, відкладене маркування Telegram-повідомлень без credentials, атомарний запис JSON, fail-closed checksum і перевірку повного набору BCK-бінарників. Додано тести fetcher та CI typecheck/test gate; retention-процес потребує ручного підтвердження; уточнено README та обмежено розмітку перекладів і CSP хабу. Перевірки наведені у підсумку змін в чаті; первинний бал і знахідки вище описують стан до виправлень.

Поточні сховища відповідають задачі: публічний `sales/data/*.json`, локальний `localStorage` Gym і SQLite, згаданий в інсталяторі BCK. **Міграція на серверну БД не обґрунтована.** Потрібно виправити інваріанти запису й відновлення та перевірити резервування даних у вихідних репозиторіях продуктів.

Перші кроки: виправити захист від порожнього Steam-каталогу й конфігурації Telegram; зробити checksum BCK обов’язковим; додати локальні перевірки цих сценаріїв і перевірку релізного пакета перед публікацією.

## 4. Детальні знахідки

### Дані та надійність

**DIST-01 — P1; БД/цілісність.** **Поточний стан:** після успішного, але порожнього Steam fetch код пише `freshSteam` у новий JSON. **Проблема:** попередні пропозиції зникають, хоча журнал каже «Keeping old data». **Докази:** `apps/sales/fetch/fetch-deals.ts:669-672` і `:926-934`; на час аудиту попередній `sales/data/deals.json` містить 11 Steam-записів. **Рекомендація:** обрати попередній список при порожньому результаті за явним правилом, відділити «немає акцій» від аномальної відповіді та не оновлювати `lastUpdated` як успішний повний refresh. **Обґрунтування/результат:** запобігає втраті каталогу через зміну upstream. **Ризик:** справді порожній каталог тимчасово залишиться stale; показувати час останнього успішного оновлення. **Складність:** мала. **Залежності:** немає. **Критерій:** тест із непорожнім old data і порожнім fetch зберігає старі Steam-записи; тест справді валідного видалення має окрему політику. **Упевненість:** висока.

**DIST-02 — P1; надійність сповіщень.** **Поточний стан:** відсутні `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` спричиняють `return` з `sendTelegramMessage`, після чого `sendBatched` викликає `markSent`. **Проблема:** повідомлення не надіслано, але історія позначає його як надіслане на період cooldown. **Докази:** `apps/sales/fetch/fetch-deals.ts:499-506`, `:827-853`, `:863-876`; workflow передає ці secrets у `.github/workflows/sales-scheduler.yml:59-61`. **Рекомендація:** для production run перевіряти конфігурацію на старті та завершуватися помилкою до зміни історії; окремий явно заданий dry-run режим може пропускати Telegram. **Результат:** немає тихої втрати сповіщень. **Ризик:** run без секретів почне падати, що є правильним сигналом конфігураційної помилки. **Складність:** мала. **Залежності:** немає. **Критерій:** негативний тест не створює нових `notifiedHistory` за відсутніх credentials. **Упевненість:** висока.

**DIST-03 — P2; БД/узгодженість.** **Поточний стан:** Telegram викликається до запису JSON; `deals.json` пишеться прямо у кінцевий файл, лише `notified-history.json` пишеться через temp+rename. **Проблема:** збій або переривання між надсиланням, двома файлами й git push лишає неузгоджений стан; можливі повторні пости. **Докази:** `apps/sales/fetch/fetch-deals.ts:827-853`, `:923-941`, `:944-956`; `.github/workflows/sales-scheduler.yml:65-80`. **Рекомендація:** атомарний temp+rename для обох JSON, перевірка схеми перед записом, durable outbox/позначення після підтвердженої публікації або хоча б документована at-least-once семантика й ідемпотентний ключ на запуск. Без зовнішньої транзакційної БД «exactly once» обіцяти не можна. **Результат:** менше часткових публікацій і контрольовані повтори. **Ризик:** зміна порядку може затримати повідомлення; потрібне відтворення переривань. **Складність:** середня. **Залежності:** DIST-01, DIST-02. **Критерій:** fault-injection перед/після кожного запису та publish не дає битого JSON і має описану поведінку повтору. **Упевненість:** висока щодо вікон збою, середня щодо їхньої production-частоти.

### Безпека дистрибуції

**DIST-04 — P1; безпека.** **Поточний стан:** BCK перевіряє `.sha256` лише якщо файл завантажився; типовий `BCK_REQUIRE_CHECKSUM` не встановлений. Далі архів розпаковується і бінарники встановлюються від root. **Проблема:** відсутній checksum не блокує встановлення; перевірка структури tar не замінює перевірку цілісності. **Докази:** `apps/bck/install.sh:25-29`, `:275-290`, `:381-388`. Це підтверджений небезпечний fallback, але не доказ підміни конкретного релізу. **Рекомендація:** fail-closed для checksum за замовчуванням, обов’язкова публікація checksum для кожного архіву; для сильнішої автентичності — підписаний маніфест із закріпленим відкритим ключем і перевіркою в інсталяторі. **Заміна:** необов’язкова SHA-256 перевірка → обов’язкова перевірка та, після підготовки ключів, підпис маніфесту. **Результат:** помилки/підміни артефакта не проходять мовчки. **Ризик:** старі релізи без checksum вимагатимуть окремого документованого legacy-шляху. **Складність:** середня. **Залежності:** інвентаризація чинних BCK assets. **Критерій:** реліз без checksum та з неправильним checksum відхиляється до встановлення; валідний проходить. **Упевненість:** висока.

**DIST-05 — P2; інсталятор.** **Поточний стан:** встановлення кожного з чотирьох BCK-бінарників завершується `|| true`; лише запуск `bckd` є обов’язковим health check. **Проблема:** CLI, agent або proxy можуть не встановитися, а інсталятор оголосить повний комплект успішним. **Докази:** `apps/bck/install.sh:381-388`, `:573-620`. **Рекомендація:** перевіряти наявність і виконуваність усіх заявлених бінарників до зупинки/заміни сервісу; невдача встановлення має зупиняти оновлення із rollback. **Результат:** реліз не лишається частково встановленим. **Ризик:** суворіша перевірка виявить неповні старі пакети. **Складність:** середня. **Залежності:** контракт складу BCK release. **Критерій:** пакет без кожного обов’язкового файлу відхиляється; старий сервіс залишається доступним. **Упевненість:** висока.

### Перевірки, DevOps і frontend

**DIST-06 — P2; тести.** **Поточний стан:** у репозиторії немає тестових файлів/тестового script для fetcher чи інсталяторів; `sales-scheduler.yml` запускає `npm ci` і `npm run fetch` із реальними зовнішніми API/Telegram, але не локальні контрактні й негативні тести. **Проблема:** регресії DIST-01/02/04/05 проходять без gate. **Докази:** `apps/sales/fetch/package.json`, `.github/workflows/sales-scheduler.yml:47-80`, перелік tracked files (`rg --files`). **Рекомендація:** мінімальні unit/contract тести для пустих/зіпсованих даних, Telegram no-credentials/429/5xx, інсталяторів з відсутнім checksum/бінарником; типізацію запускати в CI. Тести мають працювати локально і в read-only перевірці PR. **Результат:** перевірка найризикованіших гілок до публікації. **Ризик:** додаткове обслуговування моків; не підміняти ними smoke test справжнього релізу. **Складність:** середня. **Залежності:** виправлені контракти DIST-01/02/04/05. **Критерій:** ці сценарії відтворюються автоматично, `tsc --noEmit` і тести є gate. **Упевненість:** висока щодо цього репозиторію; тести в приватних source-репозиторіях невідомі.

**DIST-07 — P2; DevOps/відновлення.** **Поточний стан:** щомісячний workflow видаляє всі релізи й теги поза трьома останніми за префіксом. **Проблема:** старі сумісні артефакти недоступні для rollback або відновлення систем, які пропустили кілька оновлень; припущення «можна перебудувати з source» не є перевіреним recovery-планом. **Докази:** `.github/workflows/release-retention.yml:1-9`, `:29-49`. **Рекомендація:** перед prune затвердити retention policy за продуктом, зберігати хоча б підтримувані версії/контрольні артефакти та перевірений restore, а також журнал видалених digest. **Результат:** відтворюваний rollback для підтримуваних установок. **Ризик:** більше місця/експлуатаційного обліку. **Складність:** мала–середня. **Залежності:** інвентаризація підтримуваних версій. **Критерій:** задокументований і випробуваний restore конкретного старого релізу. **Упевненість:** висока щодо видалення, середня щодо фактичної потреби в старіших версіях.

**DIST-08 — P3; frontend-захист.** **Поточний стан:** `sales/index.html` і `gym/index.html` мають meta CSP; хаб `index.html` такої політики не має, підключає зовнішній beacon, а переклади вставляє через `innerHTML`. **Проблема:** менше захисту на випадок майбутнього небезпечного рядка перекладу чи стороннього скрипта. Зараз переклади локальні; підтвердженої XSS не знайдено. **Докази:** `index.html:15-18`, `:605-608`; `app.js:50-54`; CSP PWA у `sales/index.html:8`, `gym/index.html:8`. **Рекомендація:** текстові переклади вставляти через `textContent`, HTML дозволяти лише для явно перевірених ключів; перевірити реальні response headers і додати сумісну CSP на хабі. **Результат:** менша площа майбутньої XSS. **Ризик:** може зламати переклади з навмисними посиланнями; потрібен перелік таких ключів. **Складність:** середня. **Залежності:** інвентаризація HTML-перекладів і фактичних headers Pages/CDN. **Критерій:** CSP report-only без порушень у всіх мовах, контент відображається коректно. **Упевненість:** середня.

**DIST-09 — P3; документація.** **Поточний стан:** README заявляє «тут немає вихідного коду — лише інсталятори та готові збірки» й «12 продуктів», тоді як репозиторій містить TypeScript fetcher/Worker та `apps/catalog.json` має 10 релізних префіксів. **Проблема:** новий супроводжувач може пропустити production-логіку і сплутати кількість маркетингових позицій з релізними продуктами. **Докази:** `README.md:7-10`, `:45` (орієнтовно; рядки з описом і лічильником), `apps/sales/fetch/fetch-deals.ts`, `apps/sales/cron/src/index.js`, `apps/catalog.json`. **Рекомендація:** розрізнити 10 релізних префіксів та окремі позиції/посилання; описати, який source лежить тут, а який зовні. **Результат:** простіший супровід. **Ризик:** немає. **Складність:** мала. **Залежності:** немає. **Критерій:** README узгоджується з каталогом і workflow. **Упевненість:** висока.

## 5. Аудит БД і даних

**Висновок: залишити наявні сховища, оптимізувати узгодженість; міграцію БД не планувати.** `sales/data/deals.json` — публічний read-only snapshot (на дату аудиту 11 Steam, 45 Game Pass); `notified-history.json` — ключований журнал 400 записів. Та сама історія вбудована в `deals.json`, бо її читає клієнт (`fetch-deals.ts:923-940`); це свідоме дублювання для двох споживачів, не окрема реляційна схема. Публікація через Git має версіонування; одночасний запис захищений `concurrency` у workflow, але не транзакцією з Telegram чи git push. Основні ризики — DIST-01/02/03, а не відсутність SQL-індексів.

Gym зберігає приватні користувацькі дані локально (`apps/gym/README.md:10-12`); серверної БД тут немає. Потрібно перевірити експорт/імпорт, поведінку при очищенні браузера, квоту і відновлення у source-репозиторії та на пристроях. BCK installer задає SQLite URL і `pool_size = 10` (`apps/bck/install.sh:399-411`), що для локального daemon може бути доречним, але схема, міграції, індекси, WAL/backup/restore і реальне навантаження тут недоступні. Для PyMon/MyGit/Uptime файли даних згадані в інсталяторах, але внутрішня модель і транзакції відсутні. Стверджувати, що їхні запити повільні або схема неправильна, немає підстав. Production-БД не відкривалася.

Для остаточної оцінки потрібні source-репозиторії, схеми/міграції, обсяги БД, приклади `EXPLAIN`, результати тесту відновлення, RPO/RTO та метрики доступності. Не слід переносити JSON/localStorage/SQLite до PostgreSQL без підтвердженої потреби в багатокористувацьких транзакціях чи синхронізації.

## 7. Що залишити без змін

- Статичний HTML/CSS/JS хаб і GitHub Pages: відповідають задачі вітрини; SSR/мікросервіси не потрібні.
- Публічний JSON snapshot і локальне сховище Gym за поточної моделі без акаунтів; вирішувати питання backup, не замінювати БД автоматично.
- Піновані SHA для GitHub Actions, `npm ci`, обмежені workflow permissions і `concurrency` у sales workflow.
- Таймаути, retry/backoff та rate limiter у fetcher (`fetch-deals.ts:77-106`, `rate-limiter.ts`), а також fail-closed checksum в інсталяторах PyMon/MyGit/Uptime за типових налаштувань.
- CSP готових `sales` і `gym` PWA, code splitting у sales, семантичні атрибути доступності в хабі — наявні позитивні рішення, хоча браузерний аудит не проводився.

## 8. Що можна спростити або прибрати

- Після усунення DIST-03 оцінити, чи дві копії `notifiedHistory` потрібні обом споживачам. Зараз видаляти одну не можна: клієнт читає вбудовану, scheduler — окрему.
- Один `apps/catalog.json` уже є, але частина списків дублюється в HTML, JS і retention workflow. Поступово генерувати ці списки з каталогу або розширити `--check-catalog`, не вводячи нову платформу.
- Cloudflare Worker потрібен лише для точного hourly dispatch; якщо допустима затримка GitHub schedule, його можна прибрати разом із PAT. Це умовна оптимізація, не дефект: поточна документація прямо вказує на неприйнятні затримки.
- Не тримати у публічному README твердження про загальний стан збірок/підписів без автоматичного gate для кожного релізу.

## 9. Цільова архітектура

Зберегти монолітний статичний хаб на GitHub Pages та окремі готові PWA. Локальний/CI fetcher збирає зовнішні дані з таймаутами, перевіряє структуру і порожні відповіді, атомарно формує JSON snapshot, публікує його, а процес сповіщень має явно задокументовану at-least-once семантику й recoverable history. Релізний pipeline перевіряє склад пакета, checksum/підпис і smoke test інсталятора до публікації. GitHub Actions синхронізує версії; Cloudflare Worker лишається лише якщо потрібен точний графік. Моніторинг: час останнього успішного оновлення, кількість записів/аномально порожній результат, невдалі dispatch/fetch/publish/Telegram, checksum failure та успішність restore. Окрема серверна БД, Redis, брокер і Kubernetes тут не потрібні.

## 11. Що не варто робити

Не переписувати хаб на SSR framework, не переносити JSON до SQL, не додавати Redis/чергу/Kubernetes і не розділяти статичний сайт на сервіси без виміряного навантаження або нових вимог. Не називати будь-яку давнішу версію «вразливою» без advisory; `npm audit` поточного lockfile збирача — 0, але це вузька перевірка. Не видаляти історичні релізи, доки не підтверджено recovery policy.

## 12. Обмеження аудиту

- Код BCK, PyMon, MyGit, Uptime, Windows-продуктів і source PWA не входить до цієї папки. Схеми БД, міграції, auth, API-контракти, CVE готових бінарників, тести й збірка цих продуктів не перевірені.
- Немає доступу до production GitHub/Cloudflare settings, секретів, журналів, DNS/TLS/CDN headers, фактичних health checks, backup/restore чи метрик. Наявність workflow не доводить його успішної роботи.
- Не запускалися інсталятори, релізи, міграції, мережеве навантаження, Lighthouse або браузерні E2E. Продуктивність і Core Web Vitals потребують замірів (LCP, INP, CLS, bundle transfer, cache hit, час fetch і publish).
- `npm audit` стосується лише `apps/sales/fetch/package-lock.json` на дату перевірки; зовнішні source-репозиторії й готові assets не були охоплені. Пошук секретів у git history не проводився; у переглянутих конфігураціях виявлено посилання на secrets, не самі значення.
- Повну звірку із SITE `scripts/sync-hub.mjs --check-catalog` не виконував: SITE лежить поза межами цього аудиту. Локальна перевірка hub/retention пройшла.
