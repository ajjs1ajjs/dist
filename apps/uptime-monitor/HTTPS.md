# Власний домен і HTTPS — додаткова можливість

## Через інтерфейс — без редагування конфігу

1. Увійдіть адміністратором і відкрийте **Налаштування → DNS та HTTPS**.
2. Створіть DNS-запис свого домену на IP сервера (пояснення нижче).
3. У формі увімкніть HTTPS, введіть домен і порт. Для адреси без явного порту — 443.
4. Виберіть **Завантажити файли з комп’ютера** та два готові PEM-файли:
   сертифікат із проміжним ланцюжком і відповідний приватний ключ без пароля.
   Або виберіть **Файли вже на сервері** й введіть серверні шляхи.
5. **Перевірити без збереження** перевіряє файли в пам’яті, не записуючи їх.
   **Перевірити й зберегти** перевіряє повторно та зберігає у той самий конфіг.
6. Підготуйте DNS, фаєрвол/NAT і натисніть **Перезапустити та застосувати**.
   Підтвердьте нову адресу; після запуску відкрийте її та увійдіть знову.
7. У **Система & Бренд** оновіть адресу панелі для сповіщень.

Завантажені пари зберігаються у `tls-upload/pair-…` поруч із конфігом:
папки 0700, файли 0600, до 256 КіБ на файл. Приватний ключ не відображається
і не повертається через API. Якщо зараз HTTP, передавайте ключ лише у довіреній
локальній мережі/VPN; інакше доставте файли на сервер через SCP і задайте шляхи.

Поточна адреса продовжує працювати після збереження. Інтерфейс показує окремо
активні й збережені параметри. До перезапуску їх можна змінити та зберегти знову;
для HTTP вимкніть HTTPS і встановіть порт 8080.
Ручні зміни конфігу видно після **Оновити з конфігу**. Застаріла форма попросить
оновити дані, а інші поля конфігу та налаштування безпеки зберігаються.

Кнопка перезапуску працює для нової штатної systemd-служби з `Restart=always`
та `Environment=UPTIME_MONITOR_ALLOW_RESTART=1`. Для старої служби додайте
drop-in із кроку 4 нижче й один раз перезапустіть службу вручну. Для Docker або
ручного запуску форма покаже інструкцію перезапуску замість кнопки.

## Через конфіг — для спеціалістів

Без змін конфігурації панель працює як раніше: `http://IP-сервера:8080`.
Для звичайного HTTP домен, сертифікат і ключ не потрібні. Для HTTP з DNS-іменем
достатньо створити DNS-запис і відкривати `http://ваш-домен:8080`.

Нижче — прямий HTTPS із готовим сертифікатом для Linux зі штатною службою
`uptime-monitor`. Окремий Caddy/Nginx не потрібен. `monitor.example.com` —
умовний приклад: замініть його власним доменом у всіх кроках.

## 1. DNS

У DNS-зоні `example.com` створіть A-запис `monitor` → IP сервера.
Деякі DNS-панелі вимагають повне ім'я `monitor.example.com`.
Для інтернету це публічний IP; для офісу/VPN — внутрішній IP у DNS ваших пристроїв.
AAAA додавайте лише для робочого IPv6. Перевірка:

```bash
nslookup monitor.example.com
```

DNS не встановлює сертифікат і не задає порт.

## 2. Сертифікат і ключ

Підготуйте PEM-файли: `fullchain.pem` (сертифікат домену та проміжні
сертифікати) і відповідний `privkey.pem` (приватний ключ без пароля).
Сертифікат повинен бути чинним і покривати домен у Subject Alternative Name.
Для внутрішнього CA встановіть його кореневий сертифікат у довірені на клієнтах.
Файл PFX/P12 спочатку потрібно експортувати в окремі PEM-сертифікат і ключ.

На сервері:

```bash
sudo install -d -o root -g uptime -m 750 /etc/uptime-monitor/tls
```

Скопіюйте файли туди через SCP/WinSCP з правами адміністратора. Потім:

```bash
sudo chown root:uptime /etc/uptime-monitor/tls/fullchain.pem /etc/uptime-monitor/tls/privkey.pem
sudo chmod 640 /etc/uptime-monitor/tls/fullchain.pem /etc/uptime-monitor/tls/privkey.pem
```

Приватний ключ не публікуйте. Тримайте файли за доступним службі шляхом,
наприклад у `/etc/uptime-monitor/tls`, а не в `/root`, `/home` чи `/tmp`.

## 3. Конфігурація

```bash
sudo cp /etc/uptime-monitor/config.json /etc/uptime-monitor/config.before-https.json
sudo nano /etc/uptime-monitor/config.json
```

У наявному `server` додайте/змініть ці поля, зберігши решту полів і розділів:

```json
"server": {
  "host": "auto",
  "port": 443,
  "domain": "monitor.example.com",
  "tls": {
    "enabled": true,
    "cert_file": "/etc/uptime-monitor/tls/fullchain.pem",
    "key_file": "/etc/uptime-monitor/tls/privkey.pem"
  }
}
```

Це фрагмент JSON, між сусідніми полями/розділами потрібні коми.
Збереження у nano: Ctrl+O, Enter, Ctrl+X.

- `host: "auto"` — слухати мережеві інтерфейси сервера. Можна вказати конкретний IP.
- `domain` — власне DNS-ім'я без `https://`, порту чи `/`.
  Поле використовується для перевірки сертифіката; DNS потрібно створити окремо.
  Значення `auto` або порожнє зберігає сумісність без перевірки конкретного домену.
- `port: 443` — доступ як `https://monitor.example.com` без явного порту.
  Для `8443` адреса міститиме `:8443`.
- `tls.enabled: true` — увімкнути HTTPS. Відсутній `tls` або `enabled: false` — HTTP.
- `cert_file` та `key_file` — шляхи до PEM-файлів на сервері, бажано абсолютні.

## 4. Дозвіл порту та перевірка

Для існуючої служби один раз створіть додаткову конфігурацію systemd:

```bash
sudo mkdir -p /etc/systemd/system/uptime-monitor.service.d
sudo tee /etc/systemd/system/uptime-monitor.service.d/https.conf >/dev/null <<'EOF'
[Service]
CapabilityBoundingSet=CAP_NET_RAW CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_RAW CAP_NET_BIND_SERVICE
Restart=always
Environment=UPTIME_MONITOR_ALLOW_RESTART=1
EOF
sudo systemctl daemon-reload
```

Це дозволяє користувачу служби займати порт 443, зберігаючи право ICMP-моніторингу.
Новий інсталятор уже включає ці capabilities. Для портів вище 1023 окремий
дозвіл `CAP_NET_BIND_SERVICE` не потрібен.

Дозвольте TCP 443 у фаєрволі сервера та мережі. Для UFW:

```bash
sudo ufw allow 443/tcp
```

За NAT перенаправте TCP 443 на сервер. Переконайтеся, що порт не зайнятий.
Порт 80 для готового сертифіката не потрібен.

Перевірте конфіг і читання сертифіката від користувача служби:

```bash
sudo -u uptime /opt/uptime-monitor/uptime-monitor check-config --config /etc/uptime-monitor/config.json
```

Продовжуйте лише після `Configuration OK`. Перевірка не запускає сервер,
не потребує ліцензії та не змінює базу. Вона не підтверджує DNS, доступність
порту з мережі, зайнятість порту чи довіру браузера до CA.

## 5. Запуск

```bash
sudo systemctl restart uptime-monitor
sudo systemctl status uptime-monitor --no-pager
sudo -u uptime /opt/uptime-monitor/uptime-monitor healthcheck --config /etc/uptime-monitor/config.json
```

Відкрийте `https://monitor.example.com`. У **Налаштування → Система & Бренд**
вкажіть цю ж адресу панелі для посилань у сповіщеннях.

Застосунок використовує один listener: після перемикання на HTTPS/443 старий
HTTP/8080 закривається. HTTP→HTTPS redirect автоматично не створюється.
WebSocket сам використовує `wss://`. Для прямого HTTPS `trusted_proxies` не потрібен.

## Оновлення сертифіката та повернення HTTP

Сертифікати не отримуються й не поновлюються автоматично. До завершення строку
дії замініть обидва файли, повторіть права доступу, `check-config` і перезапуск.
Файли зчитуються під час запуску. Сертифікат/ключ потрібно переносити окремо
під час відновлення на іншому сервері; перевірте шляхи в конфігу.

Якщо запуск не вдався:

```bash
sudo journalctl -u uptime-monitor -n 50 --no-pager
```

Для відновлення конфігу, збереженого перед змінами:

```bash
sudo cp /etc/uptime-monitor/config.before-https.json /etc/uptime-monitor/config.json
sudo systemctl restart uptime-monitor
```

Або задайте `server.tls.enabled: false`, `server.port: 8080`, перезапустіть
службу й відкрийте `http://IP-сервера:8080` (порт має бути доступний у фаєрволі).

## Windows і Docker

На Windows використовуйте абсолютні шляхи виду `C:/uptime/tls/fullchain.pem`.
Команди systemd, Linux-права та capabilities не застосовуються.

У Docker можна залишити внутрішній `server.port: 8080`, увімкнути TLS і
опублікувати `-p 443:8080`. Змонтуйте файли сертифіката/ключа лише для читання,
дозвольте користувачу контейнера читати їх і вкажіть у конфігу шляхи всередині
контейнера. Вбудований healthcheck підтримує HTTP та HTTPS.
